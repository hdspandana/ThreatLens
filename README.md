# ThreatLens

ThreatLens is a **privacy-first digital abuse evidence intake, analysis, and
incident documentation assistant**. It helps someone who has received
threatening, harassing, or abusive messages move through a structured
workflow:

```
UPLOAD → PRESERVE → EXTRACT (OCR) → VERIFY → ANALYZE → ASSESS → RETRIEVE → EXPLAIN → DOCUMENT
```

This is **not a generic chatbot**. Every piece of output is labeled by its
source so a reviewer always knows:

1. What was actually found in the evidence (OCR output, file metadata)
2. What was inferred by a deterministic rule-based system (threat signals, risk score)
3. What was retrieved from a reference source (local knowledge base)
4. What was generated by an LLM (explanation text, clearly marked, with a deterministic fallback)
5. What remains uncertain (explicit uncertainty section on every risk assessment)

The system never claims that a detected signal proves a crime occurred, and
never treats a SHA-256 hash as proof of authenticity (only of storage
integrity).

## Why this stack

This project template runs on **Next.js (App Router) + TypeScript +
PostgreSQL (Drizzle ORM)**, not Python/Streamlit. The architecture below
mirrors the module boundaries of a typical Python design
(`evidence/`, `ocr/`, `text/`, `analysis/`, `risk/`, `retrieval/`, `llm/`,
`reporting/`, `schemas/`, `config/`) but implemented as TypeScript modules
under `src/lib/threatlens/`, with Next.js API routes as the thin HTTP layer
and a React UI as the thin presentation layer. Every module is independently
unit-testable and has no framework dependency except the API routes and UI.

## Architecture at a glance

```
src/lib/threatlens/
  config/settings.ts     – centralized configuration & env vars
  schemas/models.ts       – shared types/contracts (zod) for every pipeline stage
  evidence/service.ts     – upload validation, hashing, safe storage (security-critical)
  ocr/service.ts          – tesseract.js OCR wrapper, structured OcrResult
  text/processing.ts      – conservative normalization of verified text
  analysis/signals.ts     – rule-based threat/abuse signal detectors
  analysis/classifier.ts  – ThreatClassifier interface + implementations
  risk/scorer.ts          – transparent, documented severity scoring
  retrieval/service.ts    – local TF-IDF "vector index" over a reference KB
  retrieval/knowledgeBase.ts – loads data/knowledge_base/references.json
  llm/service.ts          – OpenAI-compatible explanation layer + fallback
  reporting/service.ts    – Markdown incident report generator
  repository.ts           – Drizzle/Postgres persistence (thin data-access layer)
  pipeline.ts             – wires text → signals → risk → retrieval → LLM together
  utils/textMetrics.ts    – CER/WER metrics for OCR evaluation

src/app/api/evidence/...  – HTTP routes (upload, verify, analyze, report)
src/components/ThreatLensApp.tsx – the 4-step UI (Upload → Verify → Analyze → Document)
src/db/schema.ts           – Drizzle table definitions
data/knowledge_base/       – small, labeled development reference dataset
data/evaluation/           – small, labeled development evaluation datasets
data/tessdata/              – bundled English OCR trained data (offline OCR)
eval/                       – evaluation scripts (classifier, retrieval, OCR)
tests/                      – vitest unit/integration tests
docs/                       – architecture, threat model, evaluation, limitations
```

See `docs/architecture.md` for the full data flow and design rationale.

## End-to-end workflow

1. **Upload** a screenshot (`POST /api/evidence`). The server validates the
   file (extension allow-list, magic-byte sniffing, size limit), stores the
   original bytes unmodified under a UUID-derived path (never the user's
   filename), computes a SHA-256 hash, and runs OCR immediately.
2. **Verify**: the UI shows the raw OCR text and confidence. The user edits/
   confirms it (`POST /api/evidence/:id/verify`). Raw OCR output is never
   overwritten -- the verified text is stored as a separate record.
3. **Analyze** (`POST /api/evidence/:id/analyze`) runs the full pipeline:
   text normalization → rule-based signal detection → risk scoring →
   local reference retrieval → LLM explanation (or deterministic fallback).
4. **Document**: download a Markdown report (`GET /api/evidence/:id/report`)
   containing everything above plus a disclaimer and documented limitations.

## Getting started

```bash
npm install
npx drizzle-kit push        # create tables from src/db/schema.ts
npm run dev                 # http://localhost:3000
```

Run tests:

```bash
npx vitest run
```

Run the evaluation scripts:

```bash
npx tsx eval/evaluate_classifier.ts
npx tsx eval/evaluate_retrieval.ts
npx tsx eval/evaluate_ocr.ts
```

## Environment variables

Copy `.env.example` to `.env` and adjust as needed. All configuration is
centralized in `src/lib/threatlens/config/settings.ts`.

| Variable | Purpose | Default |
|---|---|---|
| `DATABASE_URL` | PostgreSQL connection string (required) | — |
| `OPENAI_API_KEY` | Enables the LLM explanation layer | unset (deterministic fallback used) |
| `THREATLENS_LLM_ENABLED` | Feature flag for the LLM layer | `true` |
| `THREATLENS_LLM_MODEL` | Chat completions model name | `gpt-4o-mini` |
| `THREATLENS_LLM_BASE_URL` | OpenAI-compatible API base URL | `https://api.openai.com/v1` |
| `THREATLENS_STORAGE_DIR` | Where original evidence bytes are stored | `storage/evidence` |
| `THREATLENS_MAX_UPLOAD_BYTES` | Max upload size | `10485760` (10 MB) |
| `THREATLENS_OCR_ENABLED` | Feature flag for OCR | `true` |
| `THREATLENS_OCR_LANGDATA_DIR` | Local bundled tesseract trained-data dir | `data/tessdata` |
| `THREATLENS_OCR_LOW_CONFIDENCE` | Confidence threshold to warn the user | `65` |
| `THREATLENS_RISK_MEDIUM_THRESHOLD` / `_HIGH_THRESHOLD` / `_CRITICAL_THRESHOLD` | Risk score thresholds (0-10) | `2.5` / `5` / `8` |
| `THREATLENS_RETRIEVAL_ENABLED` | Feature flag for retrieval | `true` |
| `THREATLENS_RETRIEVAL_TOP_K` | Number of references returned | `3` |
| `THREATLENS_RETRIEVAL_MIN_SIMILARITY` | Minimum cosine similarity to show a result | `0.03` |

Never commit `.env`. API keys are only read server-side (`process.env`) and
are never sent to the browser.

## Security & privacy highlights

- Uploaded filenames are never used as filesystem paths (path-traversal defense).
- File type is verified by magic bytes, not just extension/declared MIME type.
- Original evidence is immutable once stored (write-once, `wx` flag) and kept
  separate from derived artifacts (OCR text, analysis, reports).
- OCR runs fully locally (tesseract.js + bundled trained data); no image
  bytes are sent to any external service during OCR.
- The LLM call (if enabled) only receives already-computed structured
  findings (verified text excerpt, detected signal categories, risk
  summary, reference titles) -- never the original image.
- Minimal logging: message content is not logged; only high-level error
  messages are logged server-side.

See `docs/threat-model.md` for the full analysis.

## Limitations (see `docs/limitations.md` for details)

- Signal detection is a transparent regex/keyword baseline, not a trained
  ML classifier. It will miss context/sarcasm and can produce false positives.
- The retrieval layer searches a small, hand-curated development knowledge
  base (`data/knowledge_base/references.json`), not a comprehensive legal database.
- No OCR accuracy number is reported because no licensed image+ground-truth
  dataset is available in this repository (see `docs/evaluation.md`).
- Nothing in this system determines legal guilt/innocence or clinical risk.
